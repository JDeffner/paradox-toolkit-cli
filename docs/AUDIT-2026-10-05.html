Release audit · 5 October 2026 · @px-lsp/cli 0.1.0

Useful for automation.
Still an early terminal interface.

pxtk covers the main research, preparation and validation loop without VS Code. Its 15 operations expose source evidence, previews and explicit failure states through both CLI and MCP. The audit found and fixed defects in argument validation, writer paths, definition detection, image sizing and log reads. The release is suitable for early use within the limits below. It does not certify gameplay or every game and platform combination.

How usable is it?

For agents and scripts, the interface is useful now: versioned JSON, described MCP inputs and output schemas, bounded lists, source continuation hashes, validation baselines, and explicit write modes reduce guesswork. It can work with bundled documentation when no game is installed, while reporting the missing coverage.

For a modder at a terminal, it needs more polish. The default display prints a short header followed by indented JSON. Help is one long command list, without command-specific help or shell completion. Initial configuration requires understanding the game folder, generated documentation, Tiger, and dependency order. The README now gives installation and initialization steps, but there is no interactive setup or guided repair command.

Indexed operations start a fresh language server for each request. In the first real CK3 run, status took about 34 seconds; later search and inspect calls took about 3 seconds each, and impact took about 8 seconds. These are observations from one machine under audit load, not a performance benchmark. MCP also serializes requests. A persistent indexed session could improve repeated research, but would need reliable invalidation before it could replace the current model.

Defects fixed before release

Finding Impact before the fix Correction
High: redirected writer root A mod root or ancestor replaced by a link after configuration resolution could redirect writes into a protected dependency. Check root ancestors and canonical containment against the mod, game and dependency roots at write boundaries. Regression cases preserve protected files.
Medium: unknown MCP fields discarded A misspelled preview-token field could disappear before validation, allowing an explicit write without the intended stale-preview check. Strict MCP objects reject unknown fields. A real client regression proves that a misspelled writer argument leaves the file unchanged.
Medium: regex definition detection A second definition on one line was missed. Nested references and matching names of other kinds could incorrectly block creation. Use the shared profile schema and definition extractor, with tests for real duplicates and false positives.
Medium: EXIF dimensions Single-dimension resizing used stored dimensions before orientation. Valid output could be rejected, or oversized output could pass the estimate. Calculate the output limit from oriented dimensions before decoding the resized pixels.
Medium: growing and rotating logs The size check preceded an unbounded read. Rotation could combine one file's identity with another file's bytes. Read bounded chunks and identity through one file handle. Tests cover oversize, growth and replacement.
Low: CLI metadata and ignored arguments JSON help/version emitted plain text; create silently ignored --kind; a literal game --json could affect CLI formatting. JSON metadata envelopes, actionable argument rejection, and option handling that respects --.
Medium: Linux process ownership The first Ubuntu run failed on an unreadable process executable. The probe took ownership from the process directory, which need not have the executable link's owner. Check ownership of the executable link itself. Keep failures visible when an executable owned by the current user cannot be inspected.

Documentation also now follows the shared localization placement policy. The plugin no longer gives an absolute rule that contradicts configured destinations. Package metadata links the source repository and issue tracker, and the distribution test exercises the installed command shim.

Remaining functional limits

  • Deep validation cannot be certified against this installation. Tiger 1.19.0 is the latest published release checked during the audit. It rejects CK3 1.20.0.3. pxtk returns exit 2, keeps findings visible and refuses baselines. Complete baseline creation and comparison have deterministic process-fixture coverage, but need a compatible real game and validator pair.
  • No gameplay proof. This audit does not start a real game. A reported running process is only an early startup observation. Victoria 3 and EU5 have automated profile coverage, not new real-game tests in this audit.
  • Launch support is bounded. Windows has actual copied-executable launch tests. Linux process detection has mocked coverage; macOS startup, alternate user-directory launch and metadata-format archive mods are unsupported. New mods still need launcher registration.
  • Research can be incomplete. Search inherits a 512-symbol cap, impact inherits a 2,000-entry override catalog cap, and dynamic references can be missed. Read-only callers are outside impact's caller list. Source paging retrieves full supported files, but match lists have no continuation cursor.
  • Preparation is selective. EU5 offers scripted-effect and scripted-trigger scaffolds, not an event template. Repeated on-action scaffold hooks with different prefixes still require manual editing when the shared target is already declared. Localization is per-key editing and coverage checking, without batch translation synchronization.
  • Image outputs have one mip level. DDS mipmap generation, texture arrays, volumes, cubemaps and animation are unsupported. Another converter is needed when the asset requires those features.
  • Disk writes have limits. Unsaved editor buffers are invisible. Each update is atomic, but a multi-file batch is not a filesystem transaction; partial failures report completed files. Use preview tokens and save relevant buffers first.

Toolkit features worth adding to the CLI

These are source-backed candidates, not features added by this audit. The comparison uses the Toolkit's integration checkout at the pinned revision and its local changes. “Tagged” means present in the local v0.5.0 source tag; it does not establish Marketplace publication. “Upcoming” means present only in the inspected integration source.

  1. Conflict reports, medium effort, upcoming. A read-only pxtk conflicts could report conflicting definitions, contributors, replace paths and dependency-order problems across an ordered mod set. The shared Compatch engine already analyzes compositions. This would extend the current single-symbol impact query. Maintained patch generation is a separate, larger feature.
  2. Safe symbol rename, medium effort, tagged. pxtk rename --file ... --line ... --column ... --to ... could wrap the existing LSP rename provider with a file preview and token. It must preserve upstream collision, ambiguity and foreign-definition refusals, and report reference-coverage limits.
  3. Translation synchronization, small to medium effort, tagged. pxtk loc sync could add a language or append missing keys while retaining translated values. Shared translation helpers already create blank entries with source comments and merge translations. This does not perform automatic translation.
  4. Exact vanilla import, small effort, upcoming. pxtk import could copy one selected game-relative file, or create one selected directory path, into the mod with exclusive creation. The editor has this workflow, but its host logic needs extraction. Directory import should retain its current meaning: create the path, not recursively copy vanilla.
  5. Migration discovery and previews, medium effort, upcoming. A catalog, route query and recipe preview could expose the shared migration engine. Require exact source/target evidence and explicit trust for local JavaScript recipes. Apply and restore are a larger follow-up; do not promise arbitrary game-version conversion.
  6. Precise definition edits, medium effort, tagged. pxtk edit could use the existing definition-edit service for property updates and block insertion while preserving comments and neighboring content. It would close the gap between creating a scaffold and maintaining it.
  7. Mod release staging, medium effort, tagged. pxtk package could show included/excluded files, metadata problems and hashes, then write a clean output directory. Existing ignore, staging and preflight modules need a shared API. Steam upload adds session and native-bridge requirements and should remain a separate proposal.

Start with translation synchronization for the smallest useful addition, or conflict reports for the largest improvement to pre-launch research. Command-specific help, clearer human output and a configuration diagnostic command would improve everyday use before adding more command groups.
